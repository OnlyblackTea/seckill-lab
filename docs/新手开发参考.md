## 0. 世界观：这个仓库是什么

`seckill-lab` 模拟一个真实大厂后端仓库。它**不是一次性写完的 demo**，而是按「工单」推进：

- 开发组（导师/AI）派给你一张张工单（见 `TASKS/`）；
- 每张工单对应一个「线上问题」+ 一个数据库八股考点；
- 你亲手改代码解决它，用验收测试（红 → 绿）证明修好了；
- 导师 review + 讲八股，然后解锁下一张工单。

你的目标不是「让代码跑起来」，而是**在解决真实问题的过程中吃透数据库原理**。

## 1. 运行环境与基础设施

### 1.1 服务拓扑

| 组件 | 说明 | 宿主机端口 |
|------|------|-----------|
| MySQL 8.0 (InnoDB) | 主数据库 `seckill_lab` | **13306** → 容器 3306 |
| Redis 7 | 缓存（Stage 5 才用） | **16379** → 容器 6379 |
| Spring Boot 应用 | 你的业务代码 | 8080 |

> ⚠️ 为什么不是默认 3306/6379？因为运行 VM 上 **5432 被别的项目占用**，为避免端口冲突，
> 本项目的 MySQL/Redis 都走 Docker 映射到非常规端口 13306/16379。`application.yml` 里
> 已用 `${DB_PORT:13306}` 之类的环境变量兜底，一般不用改。

### 1.2 启动基础设施（Docker Compose）

```bash
cd docker
docker compose up -d          # 拉起 mysql + redis
docker compose ps             # 等两个服务都变成 healthy
```

首次启动 MySQL 会自动执行 `docker/mysql/init/` 下的建表和种子脚本（01_schema.sql、02_seed.sql），
其中 02_seed.sql 会用存储过程灌 5 万行 `product` 数据（供索引/慢查询阶段观察现象），第一次可能慢十几秒。

验证种子是否就绪：

```bash
docker compose exec mysql mysql -uroot -pbagu1234 \
  -e "USE seckill_lab; SELECT COUNT(*) FROM product;"
# 期望：50003（3 条手工种子 + 50000 条批量种子）
```

一键重置（数据玩坏了就用这个）：

```bash
docker compose down -v        # -v 连数据卷一起删，下次 up 重新初始化
docker compose up -d
```

### 1.3 连接参数速查

```
MySQL:  host=localhost  port=13306  db=seckill_lab  user=root  password=bagu1234
Redis:  host=localhost  port=16379
```

如果你的**应用跑在笔记本、数据库跑在 VM（192.168.1.147）**，只需给应用设环境变量：

```bash
export DB_HOST=192.168.1.147
export REDIS_HOST=192.168.1.147
```

## 2. Spring Boot + MyBatis 上手（够用版）

### 2.1 一次 HTTP 请求在代码里怎么走

```
浏览器/模拟器
   │  GET /products/1
   ▼
ProductController        ← @RestController，负责收参数、返回 ApiResponse
   │  productService.getProduct(1)
   ▼
ProductService           ← @Service，业务逻辑、事务边界（@Transactional 打在这层）
   │  productMapper.selectById(1)
   ▼
ProductMapper (接口)      ← @Mapper 接口，只有方法签名，没有实现
   │  MyBatis 按「方法名 = statement id」去找 XML
   ▼
mapper/ProductMapper.xml ← 真正的手写 SQL 在这里
   │  JDBC → HikariCP 连接池
   ▼
MySQL (InnoDB)
```

**关键心智模型**：Mapper 接口是「声明」，XML 是「实现」。两者靠 `namespace`（= 接口全类名）
和 `id`（= 方法名）绑定。如果 XML 里没有对应的 `<select id="xxx">`，调用时才会抛
`BindingException`（启动时不报错）——本项目 Stage 1 就故意用这个机制让测试「初始为红」。

### 2.2 MyBatis 关键配置（application.yml）

```yaml
mybatis:
  mapper-locations: classpath:mapper/*.xml          # 去哪找 XML
  type-aliases-package: com.devteam.seckill.domain  # resultType 可写短名 Product
  configuration:
    map-underscore-to-camel-case: true              # category_id → categoryId 自动映射
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl  # 把真实 SQL 打到控制台
```

`log-impl: StdOutImpl` 很重要：它会把 MyBatis 实际执行的 SQL 和参数打印出来，
你调 SQL / 看索引命中时，眼睛要盯着控制台里那段 `Preparing: ...` / `Parameters: ...`。

### 2.3 连接池（HikariCP）—— 八股 primer

- 应用不会为每个请求新建一条数据库连接（太贵：TCP 握手 + MySQL 认证 + 分配线程）。
- HikariCP 预先建好一批连接放在「池」里，请求来了借一条，用完还回去。
- `maximum-pool-size: 50` 表示最多 50 条连接。**Stage 3 并发秒杀时，池大小会成为瓶颈之一**，
  届时你会亲身体会「连接数不是越大越好」。

### 2.4 事务（@Transactional）—— Stage 2 会亲手用

- Spring 的 `@Transactional` 打在 Service 方法上，方法内多次数据库操作要么全成功、要么全回滚。
- 默认只对 `RuntimeException` 回滚；受检异常需 `rollbackFor = Exception.class`。
- 底层：Spring 帮你 `setAutoCommit(false)` → 执行 → `commit()` 或 `rollback()`。
- **传播行为（propagation）**、**隔离级别（isolation）** 是 Stage 2/4 的考点，先有个印象即可。

## 3. 读懂 EXPLAIN —— Stage 1 的核心技能

在 SQL 前加 `EXPLAIN`，MySQL 会告诉你它**打算怎么执行**这条查询（还没真执行）。

```sql
EXPLAIN SELECT id, name, category_id, status, price, stock
FROM product
WHERE category_id = 10 AND status = 1 AND price BETWEEN 50 AND 200
ORDER BY price ASC LIMIT 20;
```

重点看这几列：

| 列 | 含义 | 好 / 坏 |
|----|------|--------|
| `type` | 访问类型 | 从好到坏：`const` > `ref` > `range` > `index` > **`ALL`（全表扫描，坏）** |
| `key` | 实际用到的索引 | `NULL` = 没用索引（坏）；非空 = 命中了 |
| `possible_keys` | 可能可用的索引 | 有候选但 `key=NULL`，说明优化器觉得全表更快或索引没建对 |
| `rows` | 预估扫描行数 | 越小越好 |
| `Extra` | 额外信息 | `Using index`（覆盖索引，好）；`Using filesort`（额外排序，可能坏）；`Using where` |

**Stage 1 的验收就是**：`type != ALL` 且 `key` 非空 —— 证明你的索引真的被用上了。

### 3.1 索引为什么能让查询变快（一句话八股）

InnoDB 的二级索引是一棵 **B+ 树**，按索引列有序存储。等值/范围查询能在 O(log n) 定位，
不用像全表扫描那样一行行看。但索引不是万能的，下面这些情况会「索引失效」：

- 对索引列做函数/运算：`WHERE YEAR(created_at)=2024`；
- 隐式类型转换：`WHERE varchar_col = 123`（字符串列传数字）；
- `LIKE '%xxx'` 前导通配符；
- 违反**最左前缀**：联合索引 `(a,b,c)`，只查 `WHERE b=?` 用不上；
- `OR` 连接的条件里有非索引列。

### 3.2 最左前缀 & 覆盖索引（Stage 1 会考）

- **联合索引 `(category_id, status, price)`** 相当于先按 category_id 排、再按 status 排、再按 price 排。
  查询条件必须从最左列开始连续使用，索引才有效。
- **覆盖索引**：如果查询要的列全都在索引里，MySQL 不用回表查主键，`Extra` 会显示 `Using index`，更快。

## 4. 用并发模拟器仿真前端请求

### 4.1 REST 用例（`sim/requests.http`）

用 VS Code 的 REST Client 插件（或 IDEA 的 .http 支持）打开，点每个请求上方的 `Send Request` 即可手动打接口。
适合单个请求调试、看返回 JSON。

### 4.2 并发模拟器（`SeckillLoadSimulator`，`@Tag("sim")`）

这是一个 tagged JUnit 集成测试：起 100 个线程 + 一个「起跑门」（CountDownLatch），
让它们尽可能在同一瞬间打 `POST /seckill`，用来**复现超卖**。

```bash
# 默认 Surefire 排除了 sim 分组，运行时要显式打开分组并清空排除项：
mvn test -Dgroups=sim -Dtest.excludedGroups=
```

- **Stage 0/1**：下单逻辑没实现，接口返回 501，模拟器只统计到 `notImplemented`，不断言业务。
- **Stage 3**：你会先看到「100 个请求、10 个库存，却成功了 15 单」这种超卖现象，
  然后用锁修复，再跑一次看到「成功恰好 10 单、库存 0」。这就是本模拟器的真正用途。

## 5. 跑测试（红绿驱动）

本项目用 **JUnit 5 的 `@Tag`** 给测试分阶段，用 Maven Surefire 的 `-Dgroups` 只跑某个阶段：

```bash
mvn test -Dgroups=stage00     # 骨架冒烟测试，初始就应该是【绿】
mvn test -Dgroups=stage01     # Stage 1 验收，你改代码前是【红】，改对后变【绿】
mvn test -Dgroups=sim -Dtest.excludedGroups=   # 并发模拟器
mvn test                      # 跑全部（sim 默认被排除）
```

**前置条件**：跑任何测试前，MySQL 必须已经 `docker compose up -d` 起来并 healthy。
测试连的是**真 MySQL，不是 H2**——因为 H2 没有 InnoDB 的间隙锁/MVCC/EXPLAIN 行为，
用它跑会「教错八股」。这是本项目一个重要的刻意设计。

### 5.1 测试如何做到可重复

- Stage 1 测试用 `@BeforeEach` 先 `DELETE FROM product WHERE category_id = 999901`（测试专用分类），
  再插入固定 fixture，保证每次跑数据一致。
- 索引迁移脚本 `V1__stage01_product_search_index.sql` 用 `@Sql(BEFORE_TEST_METHOD)` 自动执行，
  脚本内部是**幂等**的（先查 `information_schema.statistics` 判断索引是否已存在），重复跑不会报错。

## 6. 调试技巧

- **看真实 SQL**：控制台里 MyBatis 的 `Preparing:` / `Parameters:` 就是实际下发到 MySQL 的语句。
  把它复制到 `docker compose exec mysql mysql -uroot -pbagu1234 seckill_lab` 里手动跑、手动 EXPLAIN。
- **慢查询日志**：my.cnf 开了 `slow_query_log=ON`、`long_query_time=0.1`、`log_queries_not_using_indexes=ON`。
  ```bash
  docker compose exec mysql mysql -uroot -pbagu1234 -e "SHOW VARIABLES LIKE 'slow_query_log_file';"
  docker compose exec mysql sh -c 'tail -n 50 /var/lib/mysql/*slow.log'
  ```
- **看当前连接/事务/锁**（Stage 3/4 会频繁用）：
  ```sql
  SHOW PROCESSLIST;                              -- 当前连接在干嘛
  SELECT * FROM information_schema.innodb_trx;   -- 进行中的事务
  SHOW ENGINE INNODB STATUS\G                    -- 锁、死锁详情（innodb_print_all_deadlocks=ON）
  ```
- **看隔离级别**：`SELECT @@transaction_isolation;`（本项目默认 `REPEATABLE-READ`）。

## 8. 遇到问题怎么办

1. 先跑 `mvn test -Dgroups=stage00` 确认骨架健康、MySQL 连得上；
2. 连不上 → 检查 `docker compose ps` 是否 healthy、端口是否 13306/16379；
3. 某阶段测试红 → 这是**正常的**（工单还没做），读测试里的断言消息，它告诉你缺什么；
4. 还搞不定 → 把控制台报错、你改的文件贴给导师（我），我带你 debug。
